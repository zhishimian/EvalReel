# EvalReel 总体设计大纲

## 1. 项目定位与核心理念

EvalReel 定位于**以高并发 Benchmark 跑分与极速报告导出为主干、以 Agent 多轮轨迹评测与回放为核心壁垒**的大模型及 Agent 自动化评测平台。

- **主干场景（Benchmark 跑分）：** 覆盖纯大模型问答的高频刚需，支持零门槛批量横评与一键生成可视化战报，适用于模型选型、日常回归与横向对比。
- **差异化壁垒（Agent 多轮工具评测与回放）：** 在跑分底座之上延伸出多轮 Tool Calling 轨迹录制、离线 Mock 回放、故障注入与稳定性度量（`pass^k`），深入解决 Agent 评测成本高、外部环境不稳定及排障困难的问题。
- **统一架构抽象：** 从架构本质上，“纯大模型问答”只是“无工具调用、仅 1 轮对话”的 Agent 特例，因此整个系统基于同一套引擎与抽象层演进，无需维护两套割裂的系统。

## 2. 核心功能模块

系统划分为五大核心功能模块：前三个模块确保评测任务“又快又稳地跑完”，后两个模块负责将指标与过程“算清楚、亮出来”。

| 模块 | 核心功能 | 解决的核心痛点 |
| --- | --- | --- |
| **1. 题库与被测对象管理** | 导入 JSONL / CSV 题目集（支持文本问答与带预期工具调用的 Agent 题）；统一配置多个待测目标（如 DeepSeek、GPT、本地模型或自定义 Agent HTTP 接口）。 | 告别每次切换模型都需要修改脚本中的 URL、API Key 及题库解析代码的繁琐操作。 |
| **2. 高并发跑分引擎（主干）** | 同时向多个模型或 Agent 发起高并发批量评测；自动控制每分钟请求上限（防 `429` 限流报错）；超时自动指数退避重试；服务异常中断后支持重启断点续跑。 | 解决串行脚本耗时过长、盲目并发压垮 API、以及任务跑到中途断网导致已消耗 Token 全部作废的问题。 |
| **3. 自动化批卷引擎** | 支持两类打分器自由组合：<br>• **规则快判（免费秒出）：** 关键词匹配、正则校验、JSON 格式检查、工具名与参数精确匹配。<br>• **AI 裁判（LLM-as-a-Judge）：** 调用高能力裁判模型按预设评分标准打分并生成评语。 | 兼顾客观题的零成本确定性校验与主观题/复杂任务的语义级评估。 |
| **4. Agent 轨迹与回放（核心扩展）** | 记录 Agent 每一步的“思考 → 调工具 → 拿结果 → 最终回答”；支持将首次真实工具返回录制为**替身数据（Mock）**，后续切换模型直接离线回放；支持向工具注入延迟或报错以测试容错兜底能力；支持单题连跑 $k$ 次评估稳定性（`pass^k`）。 | 解决 Agent 评测成本高昂、外部接口返回每日波动导致对比不公平、以及难以定位第几步走偏的难题。 |
| **5. 实时看板与一键报告导出** | 评测过程中在 Web 页面或 CLI 实时展示进度条、当前速率、预计剩余时间；完成后自动统计准确率、**首字延迟（TTFT）**、**生成速度（Token/s）** 与总花费；支持选择两次历史记录做逐题对比（Diff），并**一键导出单文件 `report.html`** 直接分享。 | 跑完即可产出一份高信息密度、可直接双击打开传播的独立评测战报。 |

## 3. 系统架构与全景工程流程

以下以一次典型任务——**“使用 100 道题，同时横向对比 3 个大模型（共 300 次调用）”**为例，说明数据在 Go 后端系统中的流转全貌。

```text
[用户 / 前端页面 / CLI命令行]
       │  ① 发起请求：测这 100 道题 × 3 个模型
       ▼
┌──────────────────────────────────────────────────────────┐
│  Web 接入层 (Gin)                                        │
│  • 校验参数 -> 往 MySQL/SQLite 写 1 条“总任务” + 300 条“子任务” │
│  • 立刻返回 run_id（异步解耦，避免请求超时）             │
└──────────────┬───────────────────────────────▲───────────┘
               │ ② 投递任务ID                  │ ⑥ 实时推送进度(SSE)
               ▼                               │
┌──────────────────────────┐    ┌──────────────┴───────────┐
│ 任务队列 (Channel / Redis)│    │ 指标聚合 & 报告生成器    │
└──────────────┬───────────┘    │ • 算准确率/TTFT/花费     │
               │ ③ 抢任务        │ • 导出单文件 report.html │
               ▼                └──────────────▲───────────┘
┌──────────────────────────────────────────────┴───────────┐
│  Go 高并发调度核心 (Worker Pool，如固定 20 个 Goroutine)   │
│  ┌───────────┐    ┌──────────────┐    ┌───────────────┐  │
│  │ ④ 过限流器 │ -> │ ⑤ 执行请求   │ -> │ ⑥ 自动批卷    │  │
│  │ 令牌桶限流 │    │ • 纯LLM流式  │    │ • 规则校验    │  │
│  │ (防429)   │    │ • Agent/回放 │    │ • AI裁判打分  │  │
│  └───────────┘    └──────────────┘    └───────┬───────┘  │
└───────────────────────────────────────────────┼──────────┘
                                                │ ⑦ 结果落库
                                                ▼
                                     [SQLite / MySQL 数据库]
```

### 第 1 步：接单与异步解耦（Gin 接入层）

用户点击“开始评测”后向后端发起 `POST /api/runs` 请求。为避免在 HTTP handler 内同步循环执行 300 次调用导致 60 秒以上请求超时（504），接入层只执行毫秒级操作（50ms 内返回）：
1. 校验请求参数与目标模型/Agent 的配置及 API Key；
2. 通过 Gorm 在数据库中写入 1 条总任务记录（状态为 `Running`），并批量拆分成 300 条子任务记录（每条对应“某道题 + 某个模型”，初始状态为 `Pending`）；
3. 将 300 个子任务 ID 投递至任务队列，并立即向前端返回 `run_id`。

### 第 2 步：任务拆分与状态机（DB 落库与断点续跑）

每条子任务遵循严格的状态机流转：
`Pending（排队中）` → `Running（正在跑）` → `Success（成功）` 或 `Failed（失败）`。

当遇到程序意外崩溃或断电重启时，系统只需从数据库查询 `SELECT * FROM tasks WHERE status IN ('Pending', 'Running')`，将未完成的子任务重新放入队列继续执行；所有已标记为 `Success` 的子任务直接跳过，实现零重复消耗 Token 的断点续跑。

### 第 3 步：高并发调度、限流与退避重试（Worker Pool）

大模型评测属于典型的 I/O 密集型任务，99% 的时间处于网络等待状态：
- **固定大小 Worker Pool：** 启动固定数量的 Goroutine（如 20 个工人）共同监听任务队列（单机用 Go `Channel`，分布式用 Redis 队列），避免题目量达到万级时瞬间创建过多协程打爆本地端口、内存及上游服务。
- **令牌桶限流：** 在发请求前经过限流器取号（单机使用 Go 标准库 `rate.Limiter`，分布式使用 Redis 令牌桶），按模型商 RPM 上限（如 60 RPM）匀速放行请求，在贴近上限满速跑的同时避免触发 `429 Too Many Requests`。
- **超时控制与指数退避重试：** 为每次请求绑定 `context.WithTimeout`（如 60 秒超时）防止 Goroutine 永久阻塞；遇偶发网络抖动或临时错误时执行**指数退避重试**（第 1 次等待 1s，第 2 次 2s，第 3 次 4s；仍失败则标记为 `Failed` 并记录错误原因）。

### 第 4 步：执行器抽象层（`Runner` 接口）

通过统一的 Go `Runner` 接口屏蔽纯大模型与多轮 Agent 的调用差异：
- **模式 A：纯大模型跑分 Runner（流式 SSE）**
  强制开启流式返回（`stream: true`），以便在收到第一个字（Token）的瞬间记录 **TTFT（首字延迟）**；在完整接收后按 `生成总 Token 数 ÷ 耗时` 计算 **TPS（每秒吐字速度）**，并结合输入/输出 Token 数与模型单价核算本次调用费用。
- **模式 B：Agent 评测与回放 Runner**
  - **真实模式：** 请求直连待测 Agent 接口（或通过 Go 代理拦截 Agent 发出的大模型与工具请求），按序将每一轮的思考、调用的工具名、入参及出参持久化为一条完整 `Trace`（轨迹树）。
  - **回放模式：** 当模型输出工具调用指令时，Runner 不发起真实外部网络请求，而是从数据库提取预先录制的 Mock 替身数据直接返回给模型继续后续对话；支持按规则主动注入延时（如等待 3 秒）或模拟报错，检验 Agent 的异常处理与兜底能力。

### 第 5 步：自动批卷流水线（`Scorer` 引擎）

执行器产出结果后，立刻进入统一的 `Scorer` 批卷流程：
1. **第一关：规则快判（零成本、极速）**——校验输出是否为合法 JSON、是否包含或匹配标准答案、Agent 调用的工具名称与参数是否一致、推理/执行步数是否超限等。
2. **第二关：AI 裁判（按需开启）**——针对开放式问答、代码质量或复杂任务，将“原题 + 参考答案 + 被测输出”拼接为裁判 Prompt，经由限流池发往强裁判模型，并强制返回结构化 JSON（例如 `{"score": 8.5, "reason": "逻辑正确但漏掉了边界条件"}`）。

### 第 6 步：实时进度推送（SSE 长连接）

每当一条子任务完成并落库，系统向轻量级事件通道发送一条进度消息（如 `{done: 142, total: 300, current_tps: 48.2}`）。前端通过 **SSE（Server-Sent Events）** 与 Gin 保持单向长连接，实现进度条、实时日志与已耗费金额的平滑刷新。

### 第 7 步：聚合统计与独立战报导出（Report Exporter）

全部子任务进入终态（`Success` 或 `Failed`）后触发聚合计算：
- 汇总各模型的平均分、通过率、**P50 / P95 延迟**、平均 TTFT、平均 TPS、总 Token 消耗与总费用；
- 若启用同一题目多次重复评测，自动计算 `pass@k`（如 `pass@3`，3 遍中至少成功 1 遍的概率）与 `pass^k`（如 `pass^3`，3 遍全部成功的稳定性概率）；
- **单文件报告导出：** 使用 Go 标准库 `html/template` 将聚合统计 JSON 与前端图表代码直接内联注入预制 HTML 模板，生成**无需后端服务、双击即可在浏览器打开的独立 `report.html` 文件**，便于团队内部传阅、博客发布与测评演示。

## 4. 技术栈与分阶段演进路线

采用三步渐进式迭代策略，确保每个阶段都产出一个可运行、可演示、可发布的完整版本，避免初期被过多基础设施配置拖慢节奏。

### V1：极速跑通 Benchmark 闭环（约 2 周）
- **核心技术栈：** 纯 Go + Gin + Gorm + **SQLite**（零配置本地落库，后续切换 MySQL 仅需改动连接配置）+ 内存 `Channel` Worker Pool + `rate.Limiter`。
- **交付成果：** 支持导入 JSONL 题库，高并发横评多个（如 3 个）OpenAI 兼容大模型，支持“规则打分 + AI 裁判”，精确核算 TTFT / TPS / 调用花费，并支持一键导出单个 `report.html` 战报。

### V2：补齐生产级后端基建（约 2 周）
- **核心升级点：**
  - 存储层切换至 **MySQL** 并完成核心表索引优化；
  - 任务队列与限流器升级为 **Redis**，完善服务重启后的断点续跑及分布式限流能力；
  - 上线 **SSE 实时进度看板**，使用 `go:embed` 将前端静态资源打包进单个 Go 二进制文件；
  - 编写 Mock 大模型服务，对调度核心开展高并发压测并记录吞吐与延迟基准数据。

### V3：构建 Agent 评测与回放壁垒（约 2–3 周）
- **核心升级点：**
  - 接入多轮 Agent 评测，完整持久化 Tool Calling 轨迹树（`Trace`）；
  - 上线**透明代理录制 + 离线 Mock 回放 + 故障注入**能力；
  - 实现两次历史评测记录之间的**逐题轨迹 Diff 对比**与 `pass^k` 稳定性评估；
  - 使用 **OpenGIS-Agent** 完成一次端到端完整评测作为官方示范 Demo。
