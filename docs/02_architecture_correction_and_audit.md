# EvalReel 架构纠偏与二次红队审计报告

**审计结论（Verdict）：必须再收敛（收敛掉 MCP 代理与重型前端看板后，剩余核心可评为“硬核保留”）**

本次提出的 3 项架构纠偏修正了上一轮调研中存在物理链路错误的设计，让技术架构能够真正落地。但是，当前方案把“批量跑分驱动、大模型流式透明代理、MCP 协议代理、第 N 步读档回放、混沌故障注入、单机与 MySQL+Redis+Asynq 双引擎、独立网页报告”共 7 个大模块同时塞进 6–8 周的开发周期，对于刚学完 Go 基础语法、正在学习 Gin 和 Gorm 的开发者而言属于严重超载，强行推进必然导致每个模块都只完成一半。把 MCP 协议代理和独立前端管理台从首期 8 周目标中移出后，剩余部分结构紧凑，既能在开源社区提供真实测试价值，也符合后端研发实习的技术考察要求。

## 一、3 项核心纠偏的工程确认与残留风险检查

### 1. 纠偏 1 核查：拆清“Go 调度驱动层”与“网络代理层”的物理链路

上轮报告假设把 `OPENAI_BASE_URL`（大模型接口请求地址环境变量）指向 EvalReel 就能拦截工具调用并做离线替身（Mock）回放，这在物理链路上无法成立。对于本地运行的 Python 智能体（例如调用 GDAL 地理计算库和本地数据库的 OpenGIS-Agent），工具函数是在 Agent 进程内部直接执行本地代码，网络数据包根本不经过大模型接口代理。

纠偏后的物理链路拆分成三个边界清晰的模块：
1. **Go 调度驱动层（Orchestrator，负责发任务、管并发与批卷）：** 通过 HTTP 接口或启动带独立临时工作目录的子进程来驱动外部 Agent，负责任务拆分、超时强杀进程、断点续跑与结果打分。
2. **大模型透明流式代理层（`OPENAI_BASE_URL` 代理）：** 在不改 Agent 业务代码的前提下拦截大模型请求，录制完整多轮对话、`reasoning_content`（推理模型在给出正文前先输出的内部思考过程）、TTFT（首字延迟）、TPS（每秒生成词元数）与词元账单；同时支持在模型返回侧注入故障（例如模拟 HTTP 429 请求超限错误、网络超时、流式输出半途断开、返回格式错误的 JSON 文本），或直接返回假模型内容来低成本测试 Agent 代码本身的容错能力。
3. **工具 Mock 与故障注入的两条物理路径：**
   - **路径 A（MCP 代理）：** 专门拦截通过 MCP（Model Context Protocol，大模型连接外部工具的通用协议）发起的网络化工具调用，实现零代码侵入的工具录制、Mock 回放与故障注入。
   - **路径 B（Go 接管回放循环）：** 不启动原 Agent 进程，由 Go 程序直接读取历史录制下来的工具返回值，作为模拟输入喂给新模型或新提示词，对比不同模型在工具调用上的决策差异。

**补充指出的隐藏风险（路径 B 的硬边界）：**
路径 B 只能稳定用于**第 $N$ 步单步决策对比**（把历史前 $N-1$ 步的对话原封不动喂给新模型，观察新模型在第 $N$ 步会选什么工具、传什么参数）。只要你试图让路径 B 继续往下跑第 $N+1$ 步，一旦新模型在第 $N$ 步换了一个工具名称或修改了关键查询参数，本地保存的历史工具返回就无法匹配新请求。因此路径 B 必须明确限定为“单步读档横评”，对外文档禁止承诺“多步全程离线续跑”。

### 2. 纠偏 2 核查：收缩“回放”的实用边界

放弃“任意 Agent 都能模糊匹配实现全自动离线回放”的设想，将回放收缩到以下三个可稳定工程化的场景，是务实的选择：
1. **断点读档分叉测试（从第 $N$ 步历史上下文重跑单步或后续对比）；**
2. **确定性只读 MCP 查询类工具 Mock（仅针对参数固定或幂等查询类工具）；**
3. **代理层混沌故障注入（在网络传输层可控地制造异常）。**

**竞品交叉核验（基于联网检索资料）：**
- **第 $N$ 步读档分叉对比：** 开源 Agent 编排框架 LangGraph 原生支持“时间旅行（Time Travel）”调试功能，开发者可以通过 `get_state_history` 读取历史状态快照，并用 `update_state` 修改状态后分叉重跑（参考 [LangChain 官方文档](https://vertexaisearch.cloud.google.com/grounding-api-redirect/AUZIYQHv8PrECwODbvHOAQoWaCcAl3iKIl1kp5WoECR-Rnz3HHczTpVnnlYjnpcIZa5RdnzRjIdKo_275tj-nKev2L_i-OhFk-t9u6oKLu1c04HbSUix31rXQUObg82pXORLPCa0trjSTHWKDzFz0-JInebJC_MLfA==)）。但这项能力强绑定 LangGraph 框架，而可观测性平台 Langfuse（37,735 Stars）默认把线上采集的轨迹当做只读日志，缺少“通过透明代理零代码录下任意框架轨迹后，在命令行直接从第 $N$ 步并发横评多个新模型”的开箱工具。这是 EvalReel 可以立住的真实切入点。
- **MCP 故障注入与 Mock：** 开源社区已经出现专注该细分领域的单点工具，例如 [`mcp-chaos-monkey`](https://github.com/AlexeyTyurin/mcp-chaos-monkey)（通过检索结果确认其支持延迟、超时、畸形 JSON 等 8 类 MCP 传输层故障注入，未通过接口核实 Star 数）以及 `MockLoop/mockloop-mcp`（支持 Mock 与代理混合路由，未通过接口核实 Star 数）。这类工具目前主要是孤立的测试辅助脚本，没有整合进并发调度、批量判分和历史对比报告流水中。

### 3. 纠偏 3 核查：客观评估 Go 并发优势与 MySQL + Redis + 消息队列地位

#### Go 并发在修正架构中的 4 个实质工程优势
上轮报告仅从单个网络请求的等待耗时看待并发，低估了 Go 在系统工程层面的实际优势：

1. **高并发 SSE（服务端流式推送协议）透明代理与旁路解析：** Go 标准库中的 `net/http/httputil.ReverseProxy`（反向代理组件）配合 `http.Flusher`（强制立刻把缓冲区字节发给客户端的接口），可以在毫秒级把上游大模型吐出的每个数据块转发给 Agent 的同时，在后台协程里顺便解析 `reasoning_content` 与词元消耗；当下游 Agent 断开连接时，利用 Go 的 `context`（跨协程传递取消和超时信号的标准对象）能够瞬间级联中止向收费大模型发送的请求，避免继续产生账单。
2. **彻底避免 Python 单线程事件循环阻塞：** Python 的 `asyncio` 异步并发依赖单线程事件循环调度。在实际跑批评测时，只要自定义插件或数据保存逻辑里混入了一句同步阻塞操作（例如同步读写 SQLite、调用同步 HTTP 库或本地耗时解析），整个进程中正在运行的几百条流式连接会一起停顿，导致测出来的首字延迟指标完全失真。Go 语言的协程调度器会把并发任务分配到多个操作系统线程上执行，单点阻塞不会拖死整个调度进程。
3. **多 API Key（密钥）配额精细压榨：** 当系统需要同时管理十几个模型账号各自的每分钟请求上限（RPM）和并发连接数时，Go 在高并发计数与锁竞争上的消耗极低，没有 Python 全局解释器锁（GIL，一种同一时刻只允许一个线程执行 Python 字节码的锁机制）带来的多线程切换限制。
4. **重状态本地 Agent 的隔离编排与超时强杀：** 面对会读写本地临时文件、调用 GDAL 等底层 C/C++ 库的本地智能体（如 OpenGIS-Agent），Go 可以为每个并发任务创建独立临时工作目录；当单次评测超时时，通过操作系统级别的进程组控制（Linux 下通过系统调用 `Setpgid` 为子进程分配独立进程组，Windows 下通过系统级 Job Object 作业对象绑定进程树），把 Agent 主进程连同它拉起的所有孙进程一起干净杀掉，防止残留进程长期占用内存。

*(注：Go 依然不适合直接编写依赖 Python 科学计算库的判分逻辑，这类需求继续通过 `ExecGrader` 调用外部脚本并根据退出码判断即可。)*

#### MySQL + Redis + 消息队列的合理性确认
将分布式模式锁定为一等公民在工程上是合理的，只要服务场景明确锚定在**团队持续集成（CI）与多机并发评测**：
- **Redis Lua 原子脚本限流：** 多台机器上的执行节点（Worker）共享公司统一的模型账号池时，单机内存里的限流器无法感知其他机器的请求量，必须依靠 Redis 执行 Lua 原子脚本（将“读取当前剩余令牌、判断、扣减”打包成 Redis 内部不可分割的一步操作，防止高并发同时超发）。
- **MySQL 状态机与幂等防重：** 多节点并发消费任务时，MySQL 负责记录总任务与子任务状态流转，并依靠幂等键（Idempotency Key，确保同一批评测请求在网络重试时只会被系统创建一次的唯一标识）与数据库唯一索引防止重复扣费。
- **Asynq 分布式任务队列：** 基于 Redis 的成熟 Go 队列库 `hibiken/asynq`（13,850 Stars）能解决单机进程崩溃后内存队列任务全部丢失的问题，原生提供失败自动重试与死信队列（专门存放重试多次仍失败的任务以便人工排查的隔离队列）。

通过 `Store`（存储）、`Queue`（队列）和 `Limiter`（限流器）三个接口把本地单机实现与分布式实现隔开，个人用户依然零配置启动，团队与面试展示可以直接切换到分布式架构。

## 二、二次红队深度审计

### 1. 真实价值重审：会不会变成功能堆砌？

直接给结论：**如果把全部 7 个模块都在初版 6–8 周内堆上去，项目一定会变成每个点都浅尝辄止的功能堆砌。**
横向对比已经成型的开源工具：`Helicone`（6,293 Stars）已经做了完整的商业级代理网关与缓存；`mcpproxy-go`（430 Stars）专注 MCP 本地代理；`Promptfoo`（27,555 Stars）覆盖了丰富的 YAML（纯文本配置格式）断言与对比；`Langfuse`（37,735 Stars）把追踪看板做到了非常成熟的程度。如果一个新人用 8 周同时模仿这四个项目的局部功能，结果必然是代理没有 Helicone 稳定、MCP 协议兼容不如 mcpproxy-go、断言不如 Promptfoo 丰富、看板不如 Langfuse 好看。

**收敛后具备真实不可替代价值的核心主轴：**
把产品收敛为单一明确的工程闭环——**“面向 Agent 的流式透明录制代理、第 $N$ 步读档横评与故障注入评测引擎”**。
完整流程只有一条线：
1. Agent 挂载 EvalReel 代理端口运行并录下完整轨迹（存为压缩文件 `.jsonl.gz`）；
2. 发现某次任务在第 $N$ 步走偏时，通过 Go 调度器从该轨迹的第 $N$ 步读档，并发驱动 3 个候选模型或新提示词各跑 $k$ 遍，对比结果与工具选择差异（Diff）；
3. 开启代理层故障注入（如强制第 2 轮返回 429 或半途截断流），并发拉起隔离目录的 Agent 子进程验证容错稳定性（`pass^k`）；
4. 导出断网双击即可打开的单文件 `report.html` 战报；团队协同则通过配置切换至 MySQL + Redis + Asynq 分布式引擎。

在目前检索到的开源生态中，还没有“单文件可运行、专为 Go/Python 混合技术栈服务的 Agent 代理录制 + 第 $N$ 步分叉横评 + 故障注入 + 分布式配额调度”竞品。

### 2. 范围爆炸风险与 6–8 周工时红线核算

按当前正在学习 Gin 和 Gorm 的阶段，以每周有效编码时间 20–25 小时（6–8 周累计 140–180 小时）做务实工时拆解：

| **2. Go 调度核心 + 第 N 步读档 + 报告** | `Store`/`Queue`/`Limiter` 接口与本地实现、固定协程池、隔离子进程超时强杀、第 $N$ 步读档横评、规则/二元裁判/`ExecGrader`、`report.html` | 2.5–3 周 | 可完成 |

| **5. 独立 Web 管理后台（超载项）** | Vue/React 前端开发、前后端联调、权限与分页表格组件 | +3 周 | **严重挤占后端时间** |

#### 明确留删决策
- **硬核保留（8 周内必须写扎实）：** LLM 透明流式代理、模型侧混沌故障注入、Go 并发编排（纯大模型 / 隔离子进程 Agent / 第 $N$ 步读档分叉）、本地/分布式双底座（SQLite+Channel 与 MySQL+Redis+Asynq）、规则+二元 Pass/Fail AI 裁判+`ExecGrader`、`pass^k` 统计、单文件 `report.html`、优雅停机与 `pprof` 压测报告。
- **明确延期至 V4（8 周做完后再作为独立插件迭代）：** MCP 透明代理与 MCP 工具 Mock。原因：MCP 协议传输层细节多，与 MySQL+Redis 分布式架构同期开发会互相拖垮代码质量。
- **彻底砍掉：** 独立前后端分离 Web 控制台（全部使用命令行 + 极简 Gin 接口 + 单文件 `report.html` + 极简 SSE 进度输出）、全自动多步离线工具回放、动态用户模拟器。

### 各版本落地的关键工程细节约束

1. **V1 重点防止内存泄露与流式卡顿：**
   - 不要把整个 SSE 流读完再一次性转发，必须逐行/逐事件转发并即时调用 `Flusher.Flush()`；
   - 旁路解析尽量只保留必要字段用于计费与轨迹录制，务必使用 `go test -race` 测试上百个并发流同时断开连接时是否发生竞态崩溃或协程残留。
2. **V2 重点守住“单二进制易用性”：**
   - 保持本地模式零外部依赖（建议使用纯 Go 实现的 SQLite 驱动如 `modernc.org/sqlite`，避免 Windows 下交叉编译 CGo 报错）；
   - Gin 在 V2 主要提供任务触发、状态查询和 SSE 进度推送接口，不花费时间写复杂页面；所有报告展示统一沉淀到内嵌静态模板生成的 `report.html`。
3. **V3 重点做实大厂面试可深挖的数据指标：**
   - MySQL 状态表预先构造十万至百万条模拟子任务记录，用 `EXPLAIN` 验证按 `(run_id, status)` 查询待执行任务和聚合统计时的索引命中情况，把优化前后的耗时写进技术文档；
   - 压测必须使用自己写的模拟大模型服务端（固定 500 毫秒首字等待 + 3 秒持续流式返回 + 随机注入 5% 的 429 报错），绝不用瞬间返回 200 OK 的假接口刷高 QPS 数据；压测过程中抓取 `pprof` 内存与协程图，记录峰值内存和连接复用调优过程。
